# АгроМаркет — React

Frontend «АгроМаркета» на React + Vite. Учебный проект по дисциплине «Fullstack-разработка».

Связанные репозитории: [agromarket-server](https://github.com/Ferumit/agromarket-server) — backend
на Express (с лаб. 5), [agromarket](https://github.com/Ferumit/agromarket) — статичная версия
и `db.json` для json-server (лаб. 1–2).

## Запуск

```bash
# окно 1 — API: в папке agromarket-server (см. его README), http://localhost:3000
npm run dev

# окно 2 — этот проект, http://localhost:5173
npm install
npm run dev
```

Лабораторные 3–4 работали с json-server: `npx json-server --watch db.json --port 3001` в папке agromarket.
С лабораторной 5 он не нужен.

## Тестирование

```bash
npm test                          # компонентные тесты (Vitest + Testing Library), моки fetch
npm run coverage                  # то же с покрытием: 72 % строк, отчёт в coverage/
npx playwright install chromium   # один раз: браузер для E2E
npm run e2e                       # E2E локально: нужны npm run dev здесь и API agromarket-server
npm run e2e:prod                  # E2E (Playwright) на продакшене https://agromarket-ferumit.vercel.app
npx playwright show-report        # HTML-отчёт последнего прогона E2E
```

- Компонентные тесты лежат рядом с кодом (`src/**/*.test.jsx`), подготовка — `src/test/setup.js`,
  подмена `fetch` — `src/test/fetch.js`. Окружение — jsdom, настройки — блок `test` в `vite.config.js`.
- E2E — `e2e/buyer.spec.js`, настройки — `playwright.config.js` (адрес сайта из `E2E_BASE_URL`).
- CI (`.github/workflows/ci.yml`) в каждом PR и push в main: `npm ci` → lint → `npm test` → build.
- E2E в CI (`.github/workflows/e2e.yml`) — ежедневно в 04:00 UTC (09:00 в Астане) и кнопкой Run workflow,
  адрес продакшена — переменная репозитория `PRODUCTION_URL`. При падении отчёт и trace — в артефакте
  `playwright-report`.

## Лабораторная 3 — компоненты, props, state, hooks

- проект создан командой `npm create vite@latest agromarket-react -- --template react`, демо-счётчик удалён;
- `src/components/ProductCard.jsx` — карточка товара, данные приходят через props (`product`, `onAdd`);
- `App.jsx`: список товаров в `useState`, загрузка с json-server в `useEffect(..., [])`, вывод через `.map()` с `key`;
- поиск — управляемый (controlled) input: значение в состоянии `searchTerm`, фильтр `.filter()` + `.toLowerCase()`;
- корзина — состояние `cartCount` в App, функция `handleAddToCart` передаётся в карточку как prop (lifting state up);
- бонус: состояния `loading` и `error`, fetch обёрнут в try/catch.

### Ответы для защиты

- **Зачем `[]` в useEffect.** Второй аргумент — список зависимостей. Пустой массив означает «выполнить
  эффект один раз, после первого рендера». Без него эффект запускался бы после каждого рендера:
  `setProducts` вызывает новый рендер, тот снова запускает fetch — бесконечный цикл запросов.
- **Что такое props.** Объект с данными, который родитель передаёт компоненту снаружи:
  `<ProductCard product={product} onAdd={handleAddToCart} />`. Компонент props только читает, не меняет.
- **Controlled input.** У обычного input значение живёт в DOM, React о нём не знает. У управляемого
  значение хранится в state (`value={searchTerm}`), а `onChange` обновляет state на каждый символ —
  React решает, что показать в поле, и может сразу использовать значение (фильтр каталога).

## Лабораторная 4 — вёрстка

Сделано: семантический каркас (`Header`, `Footer`, `main` / `section` / `aside`), `src/layout.css`
(Flexbox для шапки, панели поиска и карточки, Grid для каталога и макета), mobile-first с точками
768px и 1024px, «Товар недели» на две колонки, форма оптовой заявки `ContactForm` с HTML5-валидацией.
Бонусы: `grid-template-areas`, липкая шапка и липкая «Доставка», Lighthouse Accessibility.

Старые правила раскладки из `index.css` (`.header`, `.catalog` на flex, фиксированная ширина `.card`)
удалены: они спорили с новой сеткой. Значения ниже измерены в Chromium (DevTools / Playwright).

### Box model карточки (часть 1)
- content: 220px, padding: 16px, border: 1px, margin: 0 → итоговая ширина на экране 220 + 2·16 + 2·1 = **254px**;
- с `box-sizing: border-box` ширина стала **220px**: padding и border теперь входят в `width`, content сжался до 186px;
- в дереве ЛР3 было 5 `<div>` и ни одного семантического тега — по разметке не понять, где шапка, где каталог.
  После ЛР4: `header`, `nav`, `main`, 2 × `section`, `aside`, `footer`, `address`, 12 × `article`, `<div>` осталось 3.

### repeat(4, 1fr) на узком экране (часть 4)
На ширине 500px четыре колонки не помещаются: колонка `1fr` не может стать уже содержимого карточки
(длинное слово в названии, кнопка), поэтому сетка вылезает за экран — ширина страницы 737px при окне 500px,
третья и четвёртая колонки уходят вправо, появляется горизонтальная прокрутка, карточки разной ширины.

### auto-fit vs auto-fill (часть 4)
При поиске «мол» (2 товара) на 1280px: с `auto-fit` карточки растянулись до 443px — пустые колонки
схлопываются, и два товара делят весь ряд; с `auto-fill` карточки остались 289px — пустые колонки сохраняются.
Выбран `auto-fill`: карточки одного размера при любом числе результатов поиска.

### «Товар недели» на телефоне (часть 4)
С `grid-column: span 2` без media query на 375px сетка из одной колонки достроила вторую
(`220px 153.875px`), и страница стала шире экрана (410px) — горизонтальная прокрутка. Исправлено: `span 2`
внутри `@media (min-width: 768px)`.

### Адаптивность (часть 5)
| Ширина | Колонок | Где «Доставка» | Шапка |
|--------|---------|----------------|-------|
| 375    | 1       | под каталогом  | столбик |
| 768    | 3       | под каталогом  | ряд |
| 1280   | 3       | справа от каталога | ряд |

Скриншоты: [screenshots/375.png](screenshots/375.png), [screenshots/1280.png](screenshots/1280.png).

### Форма заявки (часть 6)
Пустая форма не отправляется: браузер показывает подсказку «Заполните это поле» у имени, email и объёма
(в англоязычном Chrome — *Please fill out this field*). Email без «@» и объём 5 кг тоже останавливают
отправку (*Please include an '@'…*, *Value must be greater than or equal to 10*),
у неверного поля после ввода красная рамка (`:user-invalid`). Верно заполненная форма → alert и очистка полей.

### Бонус: Lighthouse
Accessibility: **93** → **100**. Единственное замечание — контраст плашки «Корзина»
(белый текст на полупрозрачном белом поверх зелёного, 3.82 при норме 4.5). Фон сделан тёмно-зелёным `#1b5e20`.

### Ответы для защиты
1. **section и article.** `<section>` — тематический раздел страницы со своим заголовком (каталог, форма).
   `<article>` — самостоятельный блок, который имеет смысл сам по себе, даже вырванный из страницы.
   Карточка товара самодостаточна (картинка, название, цена, кнопка), поэтому `ProductCard` — `<article>`.
2. **Один main.** `<main>` — основное содержимое документа, оно у страницы одно (для скринридера это точка
   «перейти к содержимому»). Разделов (`<section>`) внутри может быть сколько угодно.
3. **box-sizing: border-box.** `width` начинает включать padding и border. Без него к 220px добавились бы
   2·16 + 2·1 и карточка стала бы 254px — шире, чем задано.
4. **Flexbox и Grid.** Шапка — один ряд элементов (одно измерение) → Flexbox. Каталог — строки и колонки
   одновременно (два измерения) → Grid.
5. **repeat(auto-fit, minmax(220px, 1fr)).** Уместить столько колонок, сколько влезет, каждая не уже 220px,
   свободное место поделить поровну. Число колонок меняется само, без media query.
6. **Mobile-first.** Базовые стили пишутся для телефона, а для больших экранов макет «достраивается»
   через `@media (min-width: …)`: правило включается начиная с этой ширины и выше. `max-width` нужен
   при обратном подходе — от десктопа к телефону.
7. **label htmlFor и type="email".** Связка `<label htmlFor="email">` + `<input id="email">`: клик по подписи
   ставит курсор в поле, скринридер читает подпись. `type="email"` даёт встроенную проверку формата
   и клавиатуру с «@» на телефоне.

## Лабораторная 5 — каталог и форма через Express API

- `App.jsx`: константа `API_URL = 'http://localhost:3000/api'`, каталог грузится с `${API_URL}/products`
  вместо json-server;
- `ContactForm.jsx`: `handleSubmit` собирает поля через `FormData` и отправляет `POST /api/orders`
  с заголовком `Content-Type: application/json`. Ответ 201 → alert «Заявка №… принята!» и очистка формы,
  400 → alert с текстом ошибки от сервера, сервер выключен → «Сервер недоступен…»;
- бонус: пока запрос идёт, кнопка заблокирована и показывает «Отправка…».

Ответы на вопросы лабораторной 5 — в README репозитория agromarket-server.

## Лабораторная 6 — база данных (изменения в React)

Основная работа — в agromarket-server (PostgreSQL, CRUD). React-код менять не пришлось: frontend
общается с API и не знает, откуда сервер берёт данные — из файла, массива или PostgreSQL.

Бонус: в форме заявки появился `<select name="product_id">` со списком товаров из `/api/products` —
в `/api/orders` у такой заявки заполняется `product_name`.

## Лабораторная 7 — вход и защищённые запросы

- `src/api.js`: `API_URL` в одном месте и `apiFetch` — добавляет `Authorization: Bearer <токен>`,
  разбирает JSON, превращает ошибки API в исключения, при 401 с токеном выходит из аккаунта;
- `LoginForm` — вход и регистрация в одной форме (состояние `mode`), ошибка сервера под формой;
- `App.jsx`: состояние `user` (ленивая инициализация из localStorage), `handleLogin` / `handleLogout`,
  блок «Вы вошли как …» в правой колонке, проверка токена через `GET /api/auth/me` при открытии страницы;
- `AddProductForm` — новый товар, показывается только администратору;
- форма заявки отправляет запрос через `apiFetch`: если клиент вошёл, заявка привязывается к его аккаунту;
- бонусы: кнопка «Удалить» у товаров для администратора (`confirm` + `DELETE`), панель заявок `AdminOrders`
  с выбором статуса (`PATCH`).

Вид администратора: [screenshots/lab7-admin.png](screenshots/lab7-admin.png).

## Лабораторная 10 — тесты React и E2E

- **Настройка:** Vitest + jsdom + `@testing-library/react`, `jest-dom`, `user-event`, `@vitest/coverage-v8`;
  в `vite.config.js` — `environment: 'jsdom'`, `include: ['src/**/*.test.{js,jsx}']` (E2E сюда не попадают).
- **Компонентные тесты:** отрисовка по props, клики, ввод и HTML5-валидация, вызовы `onAdd` / `onDelete` /
  `onLogin` через `vi.fn()`.
- **Моки API:** `vi.spyOn(globalThis, 'fetch')` с настоящим `Response`; каталог — загрузка / данные / ошибка /
  пустой список / сеть недоступна; запрос заявки с заголовком `Authorization: Bearer test-token`; истёкший токен.
- **E2E:** Playwright, 5 сценариев на продакшене; покупатель каждый раз новый — `e2e+<время>@agromarket.test`.
- **Исправлено по итогам тестов:** «Товаров пока нет» и «ничего не найдено» в каталоге; при 401 вместо
  перезагрузки страницы (ЛР7) — событие `agromarket:session-expired` и форма входа «Сессия истекла — войдите
  заново»; у форм входа и заявки появились имена (`aria-labelledby`).

### Ответы

- **Сколько компонентных тестов и какие компоненты покрыты:** 27 тестов в 5 файлах.
  `ProductCard` — 6: название, цена с единицей, фото и заглушка без фото, «В корзину» → `onAdd(product)`,
  «Товар недели», кнопка «Удалить» только с `onDelete`.
  `LoginForm` — 7: ввод и отправка, пустые поля, e-mail без @, атрибуты пароля, ошибка сервера под формой,
  блокировка кнопки на время запроса, режим регистрации.
  `ContactForm` — 5: заявка с `Authorization: Bearer test-token`, гость без заголовка, объём меньше 10 кг,
  ошибка 400, сервер недоступен.
  `App` — 8: каталог (загрузка → товары, один запрос на `/api/products`, ответ 500, сеть недоступна, `[]`,
  поиск), истёкший токен → 401 → форма входа, вход и выход.
  Плюс 1 проверочный тест настройки (`src/test/smoke.test.jsx`). Теста «нет в наличии» нет: в таблице
  `products` нет поля `stock`.
- **Какие реальные дефекты нашли тесты:**
  1. **Пустой каталог.** Сервер вернул `[]`, и экран был просто пустым, без объяснений; поиск без совпадений
     тоже давал пустоту. Добавлены «Товаров пока нет» и «По запросу «…» ничего не найдено».
  2. **Перезагрузка при 401.** Если сервер отвечал 401 на запрос с токеном, `apiFetch` перезагружал страницу
     (`window.location.reload()`). В jsdom это `Not implemented: navigation`, и тест не мог проверить, что
     пользователь попал на вход. В браузере при этом пропадало всё введённое, например заполненная заявка.
     Теперь `apiFetch` посылает событие, `App` сбрасывает пользователя и показывает форму входа с текстом
     «Сессия истекла — войдите заново», без перезагрузки.
  3. **Два поля «Email».** Тест упал с `Found multiple elements with the text of: Email`: на странице два поля
     «Email» (вход и заявка), и формы без имени. Ни тест, ни экранный диктор не могли их различить. Формам даны
     имена по их заголовкам (`aria-labelledby`), и тесты теперь ищут `getByRole('form', { name: 'Вход' })`.

  Отдельно о пределе jsdom (это не дефект приложения): первая версия теста «пароль из 7 символов не
  отправляется» упала, потому что запрос ушёл. В jsdom атрибут `minlength` не проверяется,
  `validity.tooShort` там всегда `false`. Компонентный тест теперь проверяет только атрибуты, а саму проверку
  делает E2E в Chromium. Состояние загрузки в каталоге было ещё с ЛР3. Поля входа подписаны через
  `aria-label`, поэтому `getByLabelText` нашёл их сразу.
- **Покрытие:** 72 % строк (All files: Stmts 70,2 %, Branch 78,0 %, Funcs 63,4 %, Lines 72 %). Хуже всего покрыты
  `AddProductForm.jsx` (0 %) и `AdminOrders.jsx` (5,9 %): они показываются только администратору
  (`user.role === 'admin'`), а ни один тест не входит как администратор. `main.jsx` — тоже 0 %: это только
  точка входа (`createRoot`), а тесты рендерят `App` напрямую. Полностью покрыты `ProductCard`, `ContactForm`,
  `Header`, `Footer`, `api.js`; `LoginForm` — 100 % строк.
- **Время:** `npm test` — около 7 с на 27 тестов (Vitest: Duration 6,1–6,3 с, почти половина из них уходит на
  создание jsdom). `npm run e2e:prod` — 13–15 с на 5 тестов, если сервер не спит; в Actions — 6,5 с. На один
  тест это примерно 0,25 с против 2,8 с, то есть E2E медленнее примерно в 11 раз. Если Render спал, первый
  E2E-тест ждёт ещё 20–60 с (холодный старт в ЛР9 — 22,6 с).
- **Что увидели в trace упавшего теста:** в тесте поменяли имя кнопки `'Отправить заявку'` на
  `'Оформить заявку'`. Тест упал через 90 с: `Test timeout of 90000ms exceeded`, `waiting for getByRole('form',
  { name: 'Оптовая заявка' }).getByRole('button', { name: 'Оформить заявку' })`. В `npx playwright show-trace`:
  - слева — все шаги по порядку с временем (Navigate 0,56 с, Fill, Click, Expect…). Все прошли быстро, кроме
    `Wait for event "dialog"` (1,5 мин) и Click без времени;
  - для каждого шага — снимок страницы до и после. На последнем видна заполненная форма и кнопка «Отправить
    заявку»: сломан селектор теста, а не сайт;
  - вкладки Network (76 запросов, в том числе к API), Console, Errors и Source с подсвеченной строкой теста.
- **Почему E2E не запускаем на каждый PR:** E2E ходит на продакшен, а там ещё старая версия, так что PR проверял
  бы не свой код. Кроме того, это медленно, зависит от «сна» Render, и каждый прогон создаёт в настоящей базе
  покупателя и заявку. В компаниях E2E запускают на staging или preview-окружении, куда выкладывается именно
  код PR. Наш Preview Vercel закрыт входом и не входит в CORS (ЛР9).
- **Сколько e2e-пользователей в базе и чем это плохо:** 4 — по числу прогонов на продакшене (3 с ноутбука и
  1 ручной в Actions). Каждый прогон регистрирует ровно одного покупателя и создаёт одну заявку, а тест
  короткого пароля запрос не отправляет. Проверка в Neon SQL Editor:
  `SELECT email, created_at FROM users WHERE email LIKE 'e2e+%';`. Чем плохо: по расписанию прибавляется ещё
  покупатель и заявка каждый день. Заявки «Автотест E2E» попадают в панель администратора, искажают статистику
  (число клиентов и заявок), база растёт. Давать тесту право удалять данные на продакшене нельзя. Варианты —
  отдельная ветка Neon для E2E или ночная уборка SQL-скриптом.

### Вопросы для защиты — шпаргалка

1. **Пирамида.** Внизу много быстрых тестов: 27 компонентных React (Vitest, jsdom) и тесты сервера на Supertest
   (ЛР8, маршрут + PostgreSQL — уже интеграционный уровень). Наверху 5 E2E в Playwright. E2E мало, потому что
   каждый идёт секунды, зависит от сети и «сна» Render, падает из-за мелочей (селектор). По падению трудно
   понять, где ошибка, и каждый прогон оставляет данные в базе. Поэтому E2E — только для главных сценариев.
2. **jsdom.** Это DOM и HTML, написанные на JavaScript и работающие внутри Node.js: есть `document`, события,
   формы, `localStorage`, но ничего не рисуется. Проверить в jsdom нельзя:
   - CSS и раскладку: размеры, видимость по стилям, медиазапросы;
   - настоящую навигацию: `location.reload` — `Not implemented`;
   - часть валидации: `minlength` не работает;
   - подсказки браузера и `alert`;
   - реальную сеть и CORS.
3. **Роль и label, а не класс.** Так элемент находит пользователь и экранный диктор. Класс — деталь
   оформления: поменяли дизайн — тест упал, хотя всё работает. Если тест не находит поле по подписи, диктор
   его тоже не прочитает. У нас так нашлись два безымянных поля «Email».
4. **getBy / queryBy / findBy.**
   - `getBy` — элемент должен быть прямо сейчас, иначе ошибка;
   - `queryBy` — элемента может не быть, вернёт `null`; нужен для проверки «не показывается»;
   - `findBy` — Promise, ждёт появления элемента (по умолчанию до 1 с); нужен для данных с сервера.
5. **Мок.** Подмена настоящей зависимости управляемой: `vi.spyOn(globalThis, 'fetch')` возвращает заданный
   `Response`. Тест не зависит от сервера и его данных, идёт миллисекунды и может показать любой ответ (500,
   `[]`, обрыв сети). Риск: мок разойдётся с настоящим API (другое имя поля, другой формат ошибки). Тогда
   тесты зелёные, а сайт сломан, поэтому нужны ещё тесты сервера и E2E.
6. **Три состояния: загрузка, данные, ошибка** (и отдельно пустой список). Каждое пользователь видит
   своими глазами:
   - без загрузки на холодном старте Render — пустая страница;
   - без ошибки — вечная загрузка или пустота;
   - пустой список у нас как раз не был обработан.
7. **vi.fn().** Функция-шпион: запоминает каждый вызов и его аргументы. `toHaveBeenCalledWith(product)` —
   вызвана именно с этим товаром. `not.toHaveBeenCalled()` — не вызвана ни разу, например форма с ошибкой
   не отправилась.
8. **E2E, smoke и Supertest.** Три разных уровня:
   - Supertest (ЛР8) проверяет сервер изнутри: вызывает Express-приложение без браузера и сети, с тестовой
     базой;
   - smoke (ЛР9) — несколько HTTP-запросов к живому API после деплоя, чтобы узнать, живо ли оно;
   - E2E — настоящий браузер на продакшене проходит путь пользователя: React → API → база. Так проверяются
     сборка с `VITE_API_URL`, CORS, rewrites и вход вместе.
9. **Почему не в каждом PR.** В продакшене ещё старая версия, прогон медленный и оставляет данные в базе. В
   компаниях E2E запускают на staging или preview для каждого PR: своя выкладка и своя копия базы, например
   ветка Neon. На продакшене остаются smoke и сценарии, которые ничего не портят.
10. **Почему E2E нельзя удалять данные на продакшене.** Тест запускается автоматически, а ошибка в его условии
    удалит чужие данные. Ключ с правом удаления лежал бы в секретах CI, и его утечка означала бы возможность
    стереть базу. Принцип минимальных прав: тест создаёт только своё, а убирает за ним отдельный механизм.
11. **Покрытие.** Показывает, какие строки, ветки и функции выполнились во время тестов, — то есть где тестов
    точно нет. 100 % не значит «ошибок нет»:
    - строка могла выполниться без `expect`;
    - покрытие не видит кода, которого нет: до ЛР10 каталог мог иметь 100 % и без «Товаров пока нет»;
    - моки могут расходиться с сервером.
12. **Какой дефект нашли.** Пустой каталог без объяснений, перезагрузка страницы при 401 с потерей ввода и две
    безымянные формы с полями «Email» (подробно — в ответах выше).
